# 09 — 开发期时间加速开关

Status: resolved

## 目标

提供一个仅在开发构建生效的时间缩放机制，把 60 / 15 / 10 分钟压缩到秒级，用来快速验证整个轮次循环。

## 验收

- [x] 环境变量 `FOCUS_TIMER_SCALE` 表示缩放倍数，例如 `0.01` → 60 分钟变成 36 秒、15 分钟变成 9 秒、10 分钟变成 6 秒
- [x] **仅 debug 构建读取该变量**；release 构建忽略它，时长恒为真实值
  - 用 `#[cfg(debug_assertions)]` 或 `cfg!(debug_assertions)` 实现
- [x] 未设置该变量时（debug 与 release 都是）行为与真实时长一致
- [x] 缩放同时作用于工作、休息、重复提醒三个时长
- [x] 用 `FOCUS_TIMER_SCALE=0.01 npm run tauri dev` 能完整跑通：工作 → 提醒 → 10 分钟后重复提醒 → 确认 → 休息 → 休息结束 → 回到工作
  - 整条链路由自动化验完（`tests/dev_time_scale.rs`：同一个 `ClockThread`、同一份状态机，时长缩到 0.0001）；真机上验到前两段（工作 → 提醒 → 重复提醒），点"马上去休息"那两步在这台机器上点不了——见 Comments 的「没能验到的一截」

## 背景

- 60 分钟一轮没法手动验证。这个开关让整个轮次循环可以在几分钟内跑完
- 时长在代码里写死是产品决定（不可配置），但**开发期**仍需要一个快速验证手段——两者不冲突
- 时长常量集中在 `src-tauri/src/config.rs`，见 [`spec.md` §5.6](../spec.md)

## Comments

### 2026-10-24 — 落地了：一个环境变量 + 三层验收

**机制早就在。** 票 02 立的 `TimerConfig` 里已经有 `scaled()` 和 `from_env_or_default()`，`lib.rs` 也已经调用它。本票做的是把它变成一个**能用的开发期开关**：补上"debug 才读"的边界、补上解析的容错、补上验收。

**关键的一条：release 构建不是"看了但不用"，是那段代码根本没编进去。** `#[cfg(debug_assertions)]` 把读环境变量那段整个挡在 release 之外。打包版不可能因为谁启动时手滑带了个环境变量，就跑出 36 秒一轮的怪事。

**解析的容错**：倍率不是"有限且大于 0"的数（`abc`、`0`、`-1`、`inf`、`NaN`），或者压根没设这个变量——一律用真实时长。猜错一个倍率不该让计时器变得不可用。缩放后每个时段至少 1ms：0 长的时段会立刻到期，状态机会在原地打转。

**倍率大到离谱时封顶**（`u64::MAX / 4`）：`as u64` 碰上 `1e13` 这样的倍率会饱和成 `u64::MAX`，状态机里的 `now + work_ms` 随即溢出——debug 构建直接 panic。封顶之后，巨大倍率的后果只是"这个轮次永远走不到头"，而不是应用崩掉。**这条是 review 查出来的**：原来那句"猜错一个倍率不该让计时器变得不可用"，在 `1e13` 面前是句空话。

**分了三层，越往下越接近"真人能用的东西"**：

| 层 | 位置 | 验的是什么 |
|---|---|---|
| 纯函数 | `config.rs::from_scale_value(Option<&str>)` | 值 → 时长。不碰进程环境，所以好测 |
| 边界 | `config.rs::from_env_or_default()` | 只有 debug 构建才去读环境变量 |
| 进程级 | `tests/dev_time_scale.rs` | 环境变量真的被读到，整个轮次真的跑得通 |

**集成测试单独一个文件，是因为环境变量是进程级的。** cargo 给每个集成测试文件一个独立的可执行文件——在那里改环境变量不会漏到单元测试那边去；同一个文件里的用例用一把锁串起来。

**同一个集成测试文件同时是两种构建的验收。** debug 下断言"读到了"（`0.01` → 36 / 9 / 6 秒），release 下断言"无视了"（时长恒为真实值）。`cargo test` 和 `cargo test --release` 各验各的那一半——这比"release 的行为只在 release 构建里才被验证"要实在。

**缩放生效时应用会在终端说一句**：

```
focus-timer: 开发期缩放生效（FOCUS_TIMER_SCALE）——工作时段 36 秒 / 休息时段 9 秒 / 重复提醒 6 秒
```

不说的话应用看起来和平常一模一样，只有托盘上的数字变短了——那种"神秘地快了 60 倍"很容易被当成 bug 查半天。

### 验证分三层

1. **单元**（`config.rs` 新增 11 个（3 → 14）+ `state.rs` 新增 1 个）：倍率的数学、解析的容错、巨大倍率的封顶、缩放之后整个轮次里每一个截止时刻都对得上。
2. **进程级**（`tests/dev_time_scale.rs`，4 个用例，release 下跑 3 个）：环境变量真的被读到；整个轮次在**真时钟线程**上跑通——`0.0001` 把工作压成 360 毫秒，一条提醒一条提醒地等：工作提醒（"工作时间到"）→ 重复提醒（"还在工作？"）→ 确认 → 休息 → 休息结束（"休息结束"）→ 回到工作。断言的是**提醒的标题**而不是条数——条数只能证明"响了"，标题才能证明响的是哪一条。
3. **真机**：`FOCUS_TIMER_SCALE=0.01 npm run tauri dev` → 应用启动时打印"工作时段 36 秒 / 休息时段 9 秒 / 重复提醒 6 秒"；36 秒后托盘标题变成 `🔴 00:00`（待确认提醒）。环境变量穿过 `npm → tauri CLI → cargo → 二进制` 这条链是真的通的。

**mutation 查过了**（确认用例不是摆设）：

- 把 `from_env_or_default` 里的环境变量读取换成 `from_scale_value(None)` → 集成测试红 2 个；
- 把 `scaled()` 里的 `break_ms` 漏掉缩放 → 单元测试红 5 个（含状态机那条整个轮次的用例）；
- 把封顶去掉（`clamp` → `max`）→ `an_enormous_scale_is_capped_instead_of_overflowing` 红（left: 18446744073709551615）；
- 把集成测试里期待的提醒标题写错 → 整个轮次那条用例红。

### 没能验到的一截

真机上最后那两步——点"马上去休息"→ 休息 → 回到工作——在这台机器上点不了：截屏被系统挡了（`screencapture` 报 "could not create image from display"），AX 也看不见面板的窗口（`entire contents` 只有应用菜单和托盘项）。

这一截由第 2 层的自动化覆盖：同一个 `ClockThread`、同一份状态机，只是时长缩放了。"点确认"这个动作本身另有 `lib.rs` 里走 IPC 通道的用例（`clicking_acknowledge_starts_the_break`）。

### 已知的一处不一致

加速时**提醒文案不跟着变**：提醒里仍然写着"你已连续工作 1 小时，该休息 15 分钟了"。文案是产品定下来的常量，让它跟着倍率走就得把提醒的措辞参数化——那是另一件事（见 [`spec.md` §5.6](../spec.md)）。开发期看时长看托盘的数字。
